## Core Principles

### I. Authority & Execution Model

Claude Code is the **sole authorized agent** for all work in Phase II.

**Rules**:
- All specifications, plans, tasks, and implementations MUST be generated by Claude Code
- Manual coding by the human operator is strictly forbidden
- Claude Code MUST follow Spec-Kit Plus conventions and the Agentic Dev Stack workflow
- Any deviation from this execution model invalidates the phase

**Rationale**: Ensures consistency, traceability, and adherence to the spec-driven development methodology. Manual interventions create drift between specifications and implementation, undermining the core value proposition of the agentic workflow.

### II. Phase Boundary Enforcement (CRITICAL)

**Phase I is COMPLETE and FROZEN.**

Claude Code MUST NOT:
- Modify, refactor, or delete Phase I console application code
- Rewrite Phase I specs or history
- Reuse Phase I code directly inside Phase II runtime paths

Phase I artifacts are **read-only historical reference only**.

Phase II MUST:
- Introduce a new full-stack architecture
- Live alongside Phase I without breaking it
- Treat Phase I as a completed milestone

**Rationale**: Phase I was a learning milestone focused on in-memory console operations. Phase II is a fundamentally different architecture (full-stack web) and mixing the two would create architectural confusion. Keeping phases isolated ensures each can evolve independently and maintains clear historical context.

**Violation of this rule is a hard failure.**

### III. Mandatory Development Workflow

Phase II MUST strictly follow the **Agentic Dev Stack**:

1. Write formal specs (Spec-Kit Plus format)
2. Generate implementation plan
3. Decompose into atomic tasks
4. Implement incrementally via Claude Code
5. Validate against acceptance criteria

**Rules**:
- No step may be skipped, merged, or reordered
- All specs MUST be stored under `/specs/` according to Spec-Kit structure
- Each artifact must be validated before proceeding to the next step
- All changes must reference the originating spec requirement

**Rationale**: The workflow ensures systematic progression from user intent to validated implementation. Skipping steps leads to scope creep, misaligned implementations, and untestable outcomes.

### IV. Functional Completeness (NON-NEGOTIABLE)

Claude Code MUST implement **all five basic features**, now scoped per authenticated user:

1. Create task
2. View all tasks (user-scoped)
3. Update task
4. Delete task
5. Mark task complete / incomplete

**Rules**:
- All operations MUST enforce **task ownership**
- Users can only access and modify their own tasks
- No feature may be partially implemented
- Each feature must have defined acceptance criteria

**Rationale**: These five operations form the minimal viable product. Omitting any operation creates an incomplete user experience. User-scoping is essential for multi-user functionality and data privacy.

### V. Authentication & Security Model (MANDATORY)

Authentication is handled via **Better Auth (Frontend)** + **JWT verification (Backend)**.

**Frontend Requirements**:
- Better Auth MUST issue JWT tokens after successful authentication
- JWT MUST be attached to every API request:
  ```
  Authorization: Bearer <token>
  ```
- Frontend MUST handle token refresh and expiration gracefully

**Backend Requirements**:
- Backend MUST verify JWT signature on every request
- Backend MUST decode user identity from JWT claims
- Backend MUST enforce user ownership on all database queries
- Invalid or missing JWT → `401 Unauthorized`

**Shared Secret**:
- Both frontend and backend MUST use the same secret:
  ```
  BETTER_AUTH_SECRET
  ```
- Secret MUST be stored in environment variables, never hardcoded
- Secret MUST be sufficiently random (minimum 32 characters)

**Security Guarantees**:
- Requests without valid JWT → `401 Unauthorized`
- Users can only access their own tasks
- No shared session state between frontend and backend (stateless authentication)
- JWT expiration enforced

**Rationale**: JWT provides stateless authentication, allowing frontend and backend to scale independently. Better Auth standardizes authentication flows. Mandatory verification prevents unauthorized access and data leakage between users.

### VI. API Contract (LOCKED)

All REST endpoints MUST conform exactly to the following contract:

```
GET    /api/{user_id}/tasks                  - List all tasks for user
POST   /api/{user_id}/tasks                  - Create new task
GET    /api/{user_id}/tasks/{id}             - Get single task
PUT    /api/{user_id}/tasks/{id}             - Update task
DELETE /api/{user_id}/tasks/{id}             - Delete task
PATCH  /api/{user_id}/tasks/{id}/complete    - Toggle completion status
```

**Rules**:
- JWT user identity MUST match `{user_id}` in URL
- Backend MUST reject requests where JWT user ≠ URL user_id
- All responses MUST be valid JSON
- Errors MUST use proper HTTP status codes (400, 401, 403, 404, 500)
- All endpoints MUST return consistent error response format

**Error Response Format**:
```json
{
  "error": "string",
  "detail": "string (optional)"
}
```

**Rationale**: A locked API contract ensures frontend and backend can be developed in parallel without breaking changes. User ID in URL makes ownership explicit. Standard error formats enable consistent frontend error handling.

- Unit tests for business logic
- Integration tests for API endpoints

**Rationale**: These constraints ensure the application is secure, performant, maintainable, and follows modern best practices. They prevent common pitfalls in full-stack development.

## Development Workflow

### Agentic Dev Stack (Mandatory Process)

Every feature in Phase II MUST follow this exact sequence:

**Step 1: Specification** (`/sp.specify`)
- Write formal feature spec using Spec-Kit Plus format
- Define user stories with priorities
- Establish acceptance criteria
- Identify functional requirements
- Output: `specs/###-feature-name/spec.md`

**Step 2: Planning** (`/sp.plan`)
- Generate implementation plan based on spec
- Perform technical research
- Design data models
- Define API contracts
- Output: `specs/###-feature-name/plan.md`, `research.md`, `data-model.md`, `contracts/`

**Step 3: Task Breakdown** (`/sp.tasks`)
- Decompose plan into atomic tasks
- Organize by user story priority
- Define task dependencies
- Mark parallelizable tasks
- Output: `specs/###-feature-name/tasks.md`

**Step 4: Implementation** (`/sp.implement`)
- Execute tasks in dependency order
- Validate against acceptance criteria
- Update task status as work progresses
- Create PHRs for significant decisions
- Output: Working code + updated tasks.md

**Step 5: Validation**
- Run tests (if specified)
- Verify acceptance criteria
- Test user stories independently
- Create ADRs for architectural decisions

**Rules**:
- No step may be skipped
- Deviations must be documented with rationale
- All artifacts stored in version control
- Each step validates the previous step

**Rationale**: Systematic workflow prevents scope creep, ensures traceability, and maintains alignment between user intent and implementation.

### Prompt History Records (PHRs)

**Requirement**: Every significant user interaction MUST be recorded as a PHR.

**When to Create PHRs**:
- Implementation work (code changes, new features)
- Planning/architecture discussions
- Debugging sessions
- Spec/task/plan creation
- Multi-step workflows
- Architectural decisions

**PHR Storage** (all under `history/prompts/`):
- Constitution changes → `history/prompts/constitution/`
- Feature-specific → `history/prompts/<feature-name>/`
- General work → `history/prompts/general/`

**PHR Requirements**:
- Use template at `.specify/templates/phr-template.prompt.md`
- All placeholders must be filled
- Full user input preserved verbatim (no truncation)
- Response summary included
- Files and tests documented

**Rationale**: PHRs create an audit trail for decision-making, enable learning from past interactions, and provide context for future work.

### Architecture Decision Records (ADRs)

**Requirement**: Significant architectural decisions MUST be suggested for documentation.

**ADR Criteria** (must meet ALL three):
1. **Impact**: Has long-term consequences (framework choice, data model, API design, security, platform)
2. **Alternatives**: Multiple viable options were considered
3. **Scope**: Cross-cutting and influences system design

**Process**:
- Claude Code MUST detect significant decisions during planning/tasks
- Claude Code MUST suggest: "📋 Architectural decision detected: [brief]. Document? Run `/sp.adr [title]`"
- User MUST consent before ADR is created
- Group related decisions into single ADR when appropriate

**ADR Storage**: `history/adr/###-decision-title.md`

**Rationale**: ADRs capture the "why" behind decisions, enabling future teams to understand rationale and avoid repeating debates.

## Data Management

### Database Schema

**Users Table**:
```sql
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

**Tasks Table**:
```sql
CREATE TABLE tasks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(255) NOT NULL,
    description TEXT,
    completed BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_tasks_user_id ON tasks(user_id);
```

**Rules**:
- All queries MUST filter by `user_id` to enforce ownership
- Use UUIDs for all primary keys
- Timestamps for audit trail
- Foreign key constraints for data integrity
- Cascade delete for user removal

**Rationale**: Schema enforces multi-user isolation at the database level. UUIDs prevent enumeration attacks. Indexes ensure query performance.

### Migration Strategy

- Use Alembic (or similar) for schema migrations
- Migrations must be reversible
- Test migrations on development database before production
- Never modify existing migrations, only add new ones

**Rationale**: Controlled migrations enable safe schema evolution without data loss.
